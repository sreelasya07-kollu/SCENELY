# 0031 Tracking recovery: RECALIBRATE prompt, keyframe pause, TRACKING_LOST / TRACKING_RESET (issue #1)

- Detection lives in the core (`guide/recovery.hpp`, `TrackingRecovery`), not in ARAdapter.kt: one implementation for Android and iOS, replayable and deterministic (pose + gyro `t_ns` only). ARAdapter already forwards ARCore state + reason every frame (PAUSED -> LIMITED 2, STOPPED -> NOT_AVAILABLE 3), so it is unchanged.
- Enter: tracking not NORMAL for >= 2 s (covers PAUSED and INSUFFICIENT_FEATURES). Exit: NORMAL for >= 1 s AND gyro |omega| std-dev <= 0.35 rad/s over 1 s (no gyro samples = no evidence, never blocks), or NORMAL for 4 s regardless (never trap the user). A relapse restarts the settle wait.
- While recovering: RECALIBRATE (priority 3, `overlay_hint` "recalibrate") is the only prompt (RELOCALIZE after a long NOT_AVAILABLE loss, as before); active guidance is SUPERSEDED (not expired: no planner penalty); planning is frozen; keyframes are ignored by coverage; the session marks frames hard reject `RECALIBRATING` so no keyframe is saved. On reset the engine re-anchors (speed / turn-rate zeroed, traversal trail cut, immediate replan).
- Bundle: `/events` source `guide` records TRACKING_LOST {tracking_state, reason, degraded_s} and TRACKING_RESET {lost_s, drift_m, drift_deg}; drift = pose jump between the last NORMAL pose before and the first NORMAL pose after the loss. Shell events `tracking_lost` / `tracking_reset`. No schema change (event codes and frame reasons are free-form strings).
- Thresholds are `RecoveryParams`, deliberately NOT GuideParams fields: the gp2 hash and the replay baselines stay unchanged (the golden loss is 0.5 s; report key `recovery` and overlay key `recalibrating` appear only when used). Fold them into gp3 once tuned on device recordings (issue #1 check: CPH2381, cover then uncover the camera).
